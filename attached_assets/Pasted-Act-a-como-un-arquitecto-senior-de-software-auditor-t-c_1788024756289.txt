1. TURNOS, CLOCK IN/OUT, BREAKS Y PRODUCTIVIDAD

El sistema debe permitir que un chofer:

- Haga Clock In al comenzar a trabajar.
- Haga Start Break al tomar un descanso.
- Haga End Break cuando vuelva a trabajar.
- Haga Clock Out cuando termine el trabajo del día.
- Mantenga un historial de turnos.

Regla importante:

Mientras el chofer está Clocked In y NO está en Break, todo el tiempo cuenta como tiempo activo.

El tiempo activo incluye:

- Buscar viajes.
- Esperar demanda.
- Estar en viaje.
- Tráfico.
- Baja demanda.
- Tiempo sin ingreso.
- Tiempo lento.
- Tiempo en que el chofer se entretiene o pierde enfoque, si no ha iniciado Break.
- Tiempo necesario de operación, si el sistema no está en Break.

Solo debe detener el tiempo activo:

- Start Break.
- Receso.
- Asunto personal registrado como Break.
- Clock Out.

El sistema debe distinguir:

- Tiempo total transcurrido.
- Tiempo activo.
- Tiempo en Break.
- Tiempo con ingresos/actividad productiva, si se puede detectar.
- Tiempo disponible/sin ingreso.

Métrica central:

ingresoPorHoraActiva = ingresoBrutoAcumulado / horasActivas

Debe soportar metas configurables, por ejemplo:

- Meta mínima: $60/h.
- Meta objetivo: $65/h.
- Meta alta: $70/h.

Durante el turno debe poder calcular:

metaAcumulada = metaPorHora × horasActivas

balanceDeRitmo = ingresoAcumulado − metaAcumulada

Una hora lenta no debe considerarse un fracaso definitivo. El balance se acumula durante el turno y puede recuperarse con horas futuras más productivas.

Si se conocen las horas restantes:

ingresoNecesarioPorHoraRestante =
(metaTotalDelTurno − ingresoAcumulado) / horasActivasRestantes

El sistema objetivo debe actuar como un “cheerleader” basado en datos:

- Check-ins breves por hora.
- Mensajes positivos y concretos.
- Comparación entre ritmo real y meta.
- Cálculo de lo que falta para recuperar el ritmo.
- Proyección de cierre del turno.
- Sin avergonzar ni culpar al chofer.
- Alertas configurables si pasa demasiado tiempo activo sin ingreso registrado, con opciones para seguir trabajando, iniciar break o terminar turno.

Audita si esta lógica existe, existe parcialmente, solo aparece en UI/mock o no existe.

4. PAGOS PROGRAMADOS Y GASTOS FIJOS

Debe existir o poder construirse una estructura para:

- Upcoming Payments.
- Pagos programados.
- Gastos fijos.

Cada obligación regular debe tener:

- Nombre.
- Categoría.
- Monto.
- Frecuencia: semanal, quincenal, mensual, anual o personalizada.
- Fecha de vencimiento o regla de vencimiento.
- Próxima fecha exacta de vencimiento.
- Método de pago.
- Prioridad.
- Estado.
- Monto reservado.
- Monto pagado.
- Saldo pendiente.

Ejemplos:

- Pago del carro: $919, semanal, todos los jueves.
- Renta: monto configurable, mensual, día 19.
- Luz.
- Cable/internet.
- Teléfono.
- Seguro.
- Deudas.
- Suscripciones.

Debe distinguir claramente:

- Programado = obligación futura conocida.
- Presupuestado = límite/plan para una categoría o período.
- Reservado = dinero apartado virtualmente para una obligación.
- Pagado = dinero que realmente salió.
- Pendiente = dinero que falta reservar o pagar.

Un pago programado no puede aparecer como pagado solo porque existe dinero reservado.

Audita si esta estructura existe, dónde se define y cómo se conecta con Finance y Reports.

5. BUDGET, PROGRAMADO Y REAL

El sistema debe poder comparar, por día, semana, mes y año:

- Programado.
- Presupuesto.
- Real.

Definiciones:

- Programado: obligación o evento futuro con fecha, como pago del carro los jueves o renta el día 19.
- Presupuesto: monto planificado/límite para una categoría durante un período.
- Real: ingreso, gasto o pago confirmado y registrado.

Debe poder comparar:

- Ingresos: meta vs. ingreso real.
- Gastos: presupuesto vs. gasto real.
- Pagos fijos: programado vs. reservado vs. pagado vs. pendiente.
- Gastos no programados: separados y claramente visibles.

Audita si Finance, Budget, Ledger y Reports usan estas distinciones correctamente o si mezclan conceptos.

6. RESERVAS, DINERO COMPROMETIDO Y CASH-FLOW SAFEGUARD

La lógica objetivo requiere “cash-flow safeguard”.

Debe poder mostrar:

- Saldo bancario real, si el usuario lo registra o conecta.
- Dinero comprometido.
- Dinero reservado.
- Dinero disponible real.
- Pagos próximos.
- Cobertura de cada pago.
- Riesgo de flujo de efectivo.

Fórmula objetivo:

disponibleReal = saldoBancarioReal − dineroComprometido

Fondos virtuales/envelopes posibles:

- Carro.
- Renta.
- Impuestos.
- Mantenimiento.
- Emergencia.
- Ahorro.
- Super Plus.

Cobertura de pago:

coberturaDePago = (montoReservado / montoDelPago) × 100

Estados esperados:

- Cubierto ahora.
- Parcialmente cubierto.
- Probablemente cubierto con ingresos planificados.
- En riesgo.
- Vencido.
- Pagado.

Debe poder responder:

- “¿Tengo suficiente dinero para pagar $919 del carro este jueves?”
- “¿Cuánto falta reservar para el pago del carro?”
- “¿Con ingresos reales y planificados antes del jueves estaré cubierto?”
- “¿Después de pagar carro, renta y otros gastos, cuánto saldo libre me queda?”
- “¿Cuánto debo producir por día y por hora para cubrir pagos próximos y terminar con Super Plus?”

Audita si existe algún concepto equivalente y cómo se calcula actualmente.
